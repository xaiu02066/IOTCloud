## 2. 项目背景与目标

### 2.1 背景
智慧农业通过物联网手段对温室、大棚、田间环境进行实时感知与自动化调控。本平台面向**环境监控**场景，采集温湿度、土壤墒情等数据，并提供设备接入、远程控制、数据可视化与告警能力，降低人工巡检成本，提升农业生产精细化管理水平。

首个落地产品为**智能环境测控仪（`env_ctrl`）**：集数据采集与设备控制于一体的农业物联网终端，部署于温室大棚、种植大田，具备"本地阈值判断 + 断网声光报警 + 联网补报"能力。

### 2.2 目标
构建一个可运行的物联网云平台，支持：
- 多产品 / 多设备的统一接入与生命周期管理；
- 基于"物模型"的设备能力抽象（属性 / 事件 / 服务）；
- 遥测时序数据的上报、存储与查询；
- 平台对设备的指令下发与回执闭环；
- 面向管理人员的可视化看板与阈值告警；
- 基于 JWT + RBAC 的账号与权限体系（含种植户 / 观察员 / 管理员三类角色）。

### 2.3 术语
| 术语 | 说明 |
| --- | --- |
| 产品（Product） | 一类设备的逻辑模板，含产品标识（ProductKey）与物模型 |
| 设备（Device） | 产品下的具体物理/虚拟终端，由 **ProductKey + DeviceName** 唯一标识 |
| 物模型（Thing Model） | 设备的数字孪生定义：属性、事件、服务 |
| 属性（Property） | 设备可读/可写的状态量（如温度、湿度、阈值） |
| 事件（Event） | 设备主动上报的信息（如告警、上线/下线） |
| 服务（Service） | 平台可调用的设备能力（如下发风扇开关、设置阈值） |
| 遥测（Telemetry） | 设备周期性上报的时序数据 |
| JWT | 无状态鉴权令牌 |

## 3. 干系人需求分析

> 物模型描述"设备具备什么能力"，因此仅筛选与**设备数据采集、控制、上报**相关的需求来驱动物模型；其余（用户/权限/概览）沉淀为平台功能需求。

### 3.1 角色与场景

| 角色 | 场景 | 关注点 |
| --- | --- | --- |
| 种植户 | 管理一个或多个大棚，需远程看数据、控设备、收告警 | 易用、实时、可协作 |
| 管理员 | 平台运营方，负责产品/物模型定义与用户秩序 | 可配置、可治理 |
| 观察员 | 种植户授权的协作者（亲属/技术员） | 只读、不误操作 |

## 5. 详细功能需求

### F1 用户管理 — 注册 / 登录
- **功能描述**：提供用户注册与登录能力，登录成功后返回 JWT（access + refresh），用于后续所有接口鉴权。支持三类角色（种植户 / 观察员 / 管理员）。
- **用例**：新用户注册账号；已注册用户凭账号密码登录；Token 临近过期时刷新。
- **输入 / 输出**
  - 注册：`{username|email, password, role?}` → `{userId, username, role}`；
  - 登录：`{account, password}` → `{accessToken, refreshToken, expiresIn, userInfo}`。
- **业务规则**
  - 用户名 / 邮箱全局唯一；
  - 密码使用加盐哈希（werkzeug / bcrypt）存储，禁止明文；
  - accessToken 有效期建议 2h，refreshToken 建议 7d；
  - 角色默认"种植户"，管理员由后台分配。
- **接口建议（已实现）**：`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`。
- **验收标准**：可完成注册与登录并获取 JWT；错误密码被拒绝；Token 过期后可通过 refresh 续期；未携带有效 Token 的接口返回 401。

### F2 产品管理 — 产品 CRUD
- **功能描述**：产品是设备的逻辑分组模板，承载产品标识（ProductKey）与物模型；首个产品为 `env_ctrl` 智能环境测控仪。
- **用例**：创建 / 查询 / 修改 / 删除产品。
- **输入 / 输出**
  - 创建：`{name, product_key?, description?, thing_model?}` → `{productId, productKey, ...}`；
  - 列表（分页 + 关键字）/ 详情 / 更新 / 删除对应标准 CRUD。
- **业务规则**
  - `productKey`（产品标识）全局唯一，可由系统自动生成或用户自定义（需校验格式）；
  - 产品表同时保存**完整物模型 `thing_model` JSON**（前端一次加载）与**关系表关键字段**（运维查询）；
  - 删除产品前，若存在关联设备应拦截或提示级联影响（级联清理物模型关系表）。
- **接口建议（已实现）**：`/api/products`（GET 列表 / POST 创建 / GET 详情 / PUT 更新 / DELETE 删除）。
- **验收标准**：产品的增删改查均可用；重复 `productKey` 被拒绝；列表支持分页；删除产品级联清理其物模型关系表。

### F3 物模型 — 属性 / 事件 / 服务定义
- **功能描述**：为产品定义数字孪生能力，包含三类元素：
  - **属性**：可读 / 可写状态量（如温度、湿度、阈值）；
  - **事件**：设备主动上报的信息（如越限告警、上线/下线）；
  - **服务**：平台可调用的能力（如下发风扇开关、设置阈值）。
- **首个产品 `env_ctrl` 物模型（已冻结，详见第 6 节）**：
  - 属性 6 条：`air_temperature`、`air_humidity`、`soil_humidity`（只读）、`fan_status`（只读）、`temp_threshold`、`humid_threshold`（读写）；
  - 服务 2 条：`set_fan`、`set_threshold`；
  - 事件 4 条：`temp_alarm`、`dry_alarm`（设备端触发）、`online`、`offline`（平台感知）。
- **数据结构**
  - 属性：`{identifier, name, dataType, access_mode(只读/读写), unit, min, max}`；
  - 事件：`{identifier, name, trigger(设备端/平台), outputParams[]}`；
  - 服务：`{identifier, name, inputParams[], outputParams[]}`。
- **业务规则**
  - `identifier` 在同一产品内唯一；
  - 属性区分只读（传感器上报）与读写（可下发，如阈值）；
  - 服务定义决定 F6 指令下发的参数结构。
- **存储决策（双轨）**：`products.thing_model`（JSON）存完整模型供前端一次加载；`product_properties` / `product_services` / `product_events` 关系表存关键字段供运维 SQL 查询与管理界面；两者需保持同步。
- **接口建议（已实现）**：`/api/products/{id}/properties`、`/services`、`/events`（各自的增删改查）+ `GET /api/products/{id}/thing-model`（聚合加载）。
- **验收标准**：可定义并维护 `env_ctrl` 的 6 属性 / 2 服务 / 4 事件；物模型可被设备接入（F4）、控制（F6）、可视化（F7）正确引用。

### F4 设备管理 — 注册 / 启停 / 删除
- **功能描述**：管理设备全生命周期：注册（绑定产品）、启用、停用、删除、查看状态。设备由 **ProductKey + DeviceName** 唯一标识。
- **用例**
  - 在某产品下创建设备，系统生成设备名与设备密钥；
  - 临时停用异常设备，恢复后启用；
  - 报废设备并删除。
- **输入 / 输出**
  - 注册：`{deviceName, productId, location?, description?}` → `{deviceId, deviceName, deviceSecret, status}`；
  - 启停 / 删除：状态变更或资源移除。
- **业务规则**
  - 设备密钥安全存储，仅注册时明文返回一次；
  - 停用设备应拒绝接收遥测与下发指令；
  - 删除设备需二次确认，并清理其时序数据保留策略（可选）。
- **接口建议**：`/api/devices`（GET/POST/PUT/DELETE）、`POST /api/devices/{id}/enable|disable`。
- **验收标准**：设备可注册并与产品关联；停用后不再接收数据 / 指令；设备列表可筛选状态与位置。

### F5 时序数据 — 上报入库 / 查询
- **功能描述**：设备通过 MQTT 等协议上报遥测数据，平台解析后写入时序数据库（InfluxDB）；并提供按设备 / 时间范围的查询。
- **用例**
  - 设备周期性上报温湿度（满足 P-01、P-02）；
  - 平台查询某设备最近 24h 曲线、当前最新值。
- **输入 / 输出**
  - 上报（MQTT 主题，如 `product/{pk}/device/{dn}/upload`）：`{ts, properties:{air_temperature, air_humidity, soil_humidity, fan_status}}`；
  - 查询：`GET /api/telemetry?deviceId=&metric=&from=&to=` → 时序点数组。
- **存储设计**
  - InfluxDB：`bucket` 按环境/产品划分；`measurement` = productKey；`tag` = deviceName；`field` = 各指标。
- **业务规则**
  - 仅启用的合法设备可写入；
  - 数据写入需校验 ProductKey / DeviceSecret（或 Token）；
  - 建议按时间保留策略（如热数据 30 天、冷数据归档）。
- **接口建议**：上报经 MQTT Broker 桥接至后端消费；查询经 REST 暴露。
- **验收标准**：数据可实时写入 InfluxDB；按设备 + 时间范围查询正确；大数据量下近时效查询响应 < 1s。

### F6 设备控制 — 指令下发 / 回执
- **功能描述**：平台基于物模型"服务"向设备下发指令（如 `set_fan` 开关风机），设备执行后回执，形成闭环。
- **用例**
  - 用户在界面点击"开启风扇"，平台下发开关指令（满足 P-03）；
  - 设备回执执行结果，超时未回执则标记失败。
- **流程**
  1. 平台调用 `POST /api/devices/{id}/commands`，按物模型服务组装参数（`set_fan: {fan_state: true}`）；
  2. 经由 MQTT 下行主题推送到设备；
  3. 设备执行后上行回执（含 `messageId`）；
  4. 平台更新指令状态（成功 / 失败 / 超时）。
- **业务规则**
  - 每条指令带唯一 `messageId`，用于关联回执；
  - 超时（如 10s）未回执记为失败，可重试（限次）；
  - 仅启用设备可接收指令。
- **接口建议**：`POST /api/devices/{id}/commands`、`GET /api/devices/{id}/commands/{msgId}`。
- **验收标准**：指令可达设备并收到回执；异常（离线/超时）有记录与状态标记。

### F7 可视化 — 看板 / 曲线 / 仪表盘
- **功能描述**：前端基于 ECharts 展示实时监控看板、历史曲线与仪表盘；管理员额外可见平台级概览（A-04：设备总数、在线数、今日告警数）。
- **用例**
  - 单设备实时温湿度曲线（P-02）；
  - 多设备总览看板；
  - 阈值仪表盘（当前温度与上限对比）。
- **输入 / 输出**
  - 输入：设备选择、时间范围、刷新频率；
  - 输出：折线图、仪表盘、数字卡片、概览统计卡。
- **技术建议**
  - 前端：Vue3 + ECharts；
  - 实时数据：WebSocket（SocketIO）订阅设备最新值；
  - 历史数据：调用 F5 查询接口；概览数据：调用统计聚合接口。
- **验收标准**：曲线 / 仪表盘正确渲染；实时数据自动刷新；多设备视图可切换；管理员概览卡数据准确。

### F8 告警 — 规则 / 触发 / 记录
- **功能描述**：提供阈值告警引擎，用户配置规则，数据流入时评估并触发告警，记录告警流水。告警规则**独立建表** `alarm_rules`（与物模型解耦）。
- **用例**
  - 配置规则"空气温度 > 35℃ → 严重告警"（满足 P-04）；
  - 越限触发，生成告警记录可供查询（满足 P-05）。
- **输入 / 输出**
  - 规则（独立表）：`{product_id, device_id(可空=产品级), rule_name, metric, operator(> < >= <= == !=), threshold, level(warning/critical), enabled, description}`；
  - 记录（事件表）：`{ruleId/eventId, deviceId, value, triggeredAt, level, status}`。
- **业务规则**
  - 规则绑定到产品（或具体设备）；
  - 支持持续时长（防抖）避免抖动产告警；
  - 触发后可执行动作（记录 / 通知 / 界面提示，初版至少"记录 + 界面提示"）。
- **接口建议**：`/api/alarm-rules`（CRUD）、`/api/alerts`（查询）。
- **验收标准**：规则可配置；越限正确触发并落库；告警历史可按设备 / 时间查询。
- **已建示例规则**：温度超限 `air_temperature > 35`；土壤湿度低 `soil_humidity < 20`。

### F9 权限 — RBAC 拦截
- **功能描述**：基于角色的访问控制，在接口层对资源进行角色 / 权限拦截，区分种植户、观察员、管理员。
- **用例**
  - 种植户仅能查看自己名下产品 / 设备（行级隔离）；
  - 观察员仅可查看被授权数据，不能控制设备（O-02）；
  - 管理员拥有全部操作权限（A-03）；
  - 未登录或越权访问返回 403。
- **模型**：用户 — 角色 — 权限；JWT 携带 `userId` 与 `roles`。
- **权限项示例**：`product:manage`、`device:control`、`alert:config`、`user:admin`、`device:view_shared`（观察员）。
- **业务规则**
  - 公共接口（登录、注册、物模型只读聚合）免鉴权；
  - 数据级权限：种植户仅访问归属资源（行级隔离），观察员仅访问被授权资源；
  - 角色可配置，默认预置"管理员 / 种植户 / 观察员"。
- **接口建议**：鉴权中间件统一拦截；权限元数据可配置化。
- **验收标准**：未登录返回 401；越权返回 403；不同角色看到的功能与数据范围正确。

## 6. 物模型定义（首个产品 `env_ctrl`）

### 6.1 产品与设备的关系
- **产品（Product）**：设备的逻辑模板（如"智能环境测控仪"车型）。
- **设备（Device）**：产品的具体实例，每个设备通过 **ProductKey + DeviceName** 唯一标识（类比"车牌"）。

### 6.2 物模型三要素

| 要素 | 数据的流动方向 | 谁发起 | 例 |
| --- | --- | --- | --- |
| 属性 | 设备 → 平台 | 设备主动上报 | 温度、湿度、开关状态 |
| 服务 | 平台 → 设备 | 平台主动调用 | 打开开关、设置阈值 |
| 事件 | 设备 → 平台 | 设备检测到异常主动上报 | 超温告警、设备上线 |

### 6.3 产品定义

| 项目 | 内容 |
| --- | --- |
| 产品名称 | 智能环境测控仪 |
| 产品标识 | `env_ctrl` |
| 产品定位 | 集数据采集与设备控制于一体的农业物联网终端 |
| 部署位置 | 温室大棚、种植大田 |

### 6.4 属性（6 条）

| 序号 | 属性名称 | 标识符 | 数据类型 | 单位 | 读写类型 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 空气温度 | `air_temperature` | float | °C | 只读 | 传感器采集上报 |
| 2 | 空气湿度 | `air_humidity` | float | %RH | 只读 | 传感器采集上报 |
| 3 | 土壤湿度 | `soil_humidity` | float | % | 只读 | 传感器采集上报 |
| 4 | 风机状态 | `fan_status` | bool | - | 只读 | true=运转，false=停止 |
| 5 | 温度告警阈值 | `temp_threshold` | float | °C | 读写 | 用户设定，设备本地存储 |
| 6 | 湿度告警阈值 | `humid_threshold` | float | % | 读写 | 用户设定，设备本地存储 |

> **为什么阈值是"读写属性"而非纯服务端配置**：P-04 要求断网也能报警，故告警判断必须在设备端执行，设备需本地存储阈值；用户改阈值后平台下发到设备（亦可由 F3 服务 `set_threshold` 批量同步）。

### 6.5 服务（2 条）

| 序号 | 服务名称 | 标识符 | 输入参数 | 输出参数 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 1 | 风机控制 | `set_fan` | `fan_state`（bool，必填） | `result`（string） | true=开，false=关 |
| 2 | 设置告警阈值 | `set_threshold` | `temp_max`（float）、`humid_min`（float） | `result`（string） | 批量设置两个告警线 |

### 6.6 事件（4 条）

| 序号 | 事件名称 | 标识符 | 触发位置 | 输出参数 | 触发条件 |
| --- | --- | --- | --- | --- | --- |
| 1 | 温度超限告警 | `temp_alarm` | 设备端 | `temperature`、`threshold`、`timestamp` | 温度 > 本地存储阈值 |
| 2 | 土壤湿度低告警 | `dry_alarm` | 设备端 | `humidity`、`threshold`、`timestamp` | 湿度 < 本地存储阈值 |
| 3 | 设备上线 | `online` | 平台 | `timestamp` | 设备连接成功，平台感知 |
| 4 | 设备下线 | `offline` | 平台 | `timestamp` | 心跳超时，平台感知 |

## 8. 数据模型设计决策

### 8.1 物模型双轨存储
- **产品表 `products.thing_model`（JSON 列）**：存完整物模型（产品 + 属性 + 服务 + 事件），前端一次加载，省多次请求。
- **关系表 `product_properties` / `product_services` / `product_events`**：存关键字段（identifier、data_type、access_mode、trigger 等），便于 SQL 精确查询、运维统计与管理界面列表展示。
- **一致性**：更新物模型时需同时维护 JSON 与关系表（建议封装统一"保存物模型"方法保证同步）。

### 8.2 告警规则独立建表
- **`alarm_rules`** 单独建表：告警规则是"用户配置的阈值实例"，与物模型（设备能力定义）不同，不应混在 `thing_model` 内；
- 字段：`product_id`、`device_id`（NULL=产品级，适用该产品所有设备）、`rule_name`、`metric`（监测属性标识符）、`operator`、`threshold`、`level`（warning/critical）、`enabled`、`description`；
- 与 `device_events`（告警触发流水）分离：本表是"规则定义"，`device_events` 是"触发记录"。

### 8.3 已落地表清单（MySQL `iotcloud`）
`products`（含 `thing_model` JSON）、`devices`、`product_properties`、`product_services`、`product_events`、`device_property_values`（读写型属性）、`device_commands`（F6 指令）、`device_events`（F8 触发记录）、`alarm_rules`（F8 规则）。建库脚本见 `db/init_iotcloud.sql`。

## 10. 技术架构建议（参考）

```
设备(传感器/控制器)  ── env_ctrl 智能环境测控仪
   │  MQTT(TLS)
   ▼
EMQX(MQTT Broker) ──桥接──▶ 后端服务(Flask: 认证/设备/物模型/控制)
                                │
            ┌───────────────────┼───────────────────┐
            ▼                   ▼                   ▼
        MySQL(业务/用户/        InfluxDB(时序)      Redis(缓存/Session)
        产品/设备/权限/          air_temperature/     │
        物模型/告警规则)         air_humidity/...     │
            │                                        │
        前端(Vue3+ECharts) ◀── REST / WebSocket ──────┘
```

- **后端**：Python + **Flask**（已落地 F1/F2/F3 骨架与 CRUD）
  - `Flask-JWT-Extended`（F1 鉴权）、`Flask-SQLAlchemy` + `PyMySQL`（MySQL 业务/物模型）、`paho-mqtt`（F5 消费 EMQX）、`Flask-SocketIO`（F7 实时）、`Flask-Caching`/Redis、`Flask-CORS`。
- **消息**：EMQX（MQTT Broker）
- **存储**：MySQL（业务/物模型/告警规则） + InfluxDB（时序） + Redis（缓存/限流）
- **前端**：Vue3 + ECharts；实时用 WebSocket
- **部署**：Docker / Docker Compose（Flask 应用容器化），后续可上 K8s

## 12. 风险与待确认事项

1. 设备侧协议：确认上报采用 MQTT 还是 CoAP / HTTP；是否需兼容 Modbus 网关。

4. 多租户：初稿按单租户设计，是否需多租户隔离待确认。
5. 告警动作：初版仅"记录 + 界面提示"，是否接入短信 / 邮件 / 微信通知需确认。
6. 物模型双写一致性：JSON 与关系表同步机制需明确（建议统一服务层封装）。
7. 观察员授权模型：P-06 的"添加观察员"需定义授权关系表（用户—设备/产品授权），本版暂未细化。
