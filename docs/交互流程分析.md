## 1. 文档说明

需求清单 v2.0 已完成**行为视角（第 5 节用例）**与**结构视角（第 6 节模块）**分析。本文档从**动态视角**补全第三层：各类角色与系统、系统各模块之间在典型业务场景下的**消息时序、数据流向与异常处理**，支撑后续详细设计与接口/状态机设计。

本文不再重复用例规约与模块职责，而是以**时序图 + 说明**的形式回答"一次操作在系统内部是怎么流动的"。

### 1.1 参与者与图例约定

| 符号 | 含义 |
| --- | --- |
| `参与者` | 人角色（种植户 / 观察员 / 管理员）或外部系统（设备 env_ctrl） |

## 2. 认证与授权流程（IF-01）

登录是几乎所有后续流程的前置。本流程刻画"登录获取 JWT → 访问受保护接口 → 刷新令牌"三阶段。

```mermaid
sequenceDiagram
    participant U as 用户(种植户/观察员/管理员)
    participant FE as 前端
    participant M1 as M1 用户与鉴权
    participant M9 as M9 权限
    participant DB as MySQL(users)

    U->>FE: 输入账号密码
    FE->>M1: POST /api/auth/login {account,password}
    M1->>DB: 查询用户并取密码哈希
    DB-->>M1: 用户记录
    alt 凭据错误
        M1-->>FE: 401 凭据错误
    else 账号被冻结
        M1-->>FE: 403 账号已冻结
    else 校验通过
        M1->>M9: 读取角色 role
        M9-->>M1: 角色信息
        M1->>M1: 生成 accessToken(2h) + refreshToken(7d)
        M1-->>FE: {accessToken, refreshToken, userInfo}
        FE->>FE: 本地保存 token
    end
```

受保护接口访问与刷新（令牌续期）：

```mermaid
sequenceDiagram
    participant FE as 前端
    participant M1 as M1 用户与鉴权
    participant M9 as M9 权限
    participant API as 业务模块(M2~M8)

    FE->>M1: 请求带 Authorization: Bearer <accessToken>
    M1->>M9: 校验 JWT 签名与有效期
    alt token 失效/缺失
        M9-->>FE: 401 未认证
    else 通过
        M9-->>M1: 放行(携带 userId, role)
        M1->>API: 调用业务接口
        API-->>FE: 业务数据
    end
    Note over FE,M1: accessToken 临近过期
    FE->>M1: POST /api/auth/refresh {refreshToken}
    M1-->>FE: 新 accessToken
```

**要点**
- 角色在登录时由 M9 读取，注入 JWT `claims`，后续每个请求由 M9 中间件校验，无需每次查库（Redis 可缓存黑名单）。
- 本流程当前已落地 F1（注册/登录/JWT 签发），但 **M9 角色拦截尚未实现**（v2.0 实现状态：F9 ⬜），故"放行"目前不含角色判定。

## 3. 产品与物模型定义流程（IF-02）

管理员先建产品，再为产品定义物模型。本流程强调 **JSON 与关系表双写一致**（数据模型决策 10.1）。

```mermaid
sequenceDiagram
    participant A as 管理员
    participant FE as 前端
    participant M2 as M2 产品管理
    participant M3 as M3 物模型
    participant DB as MySQL(products/关系表)

    A->>FE: 填写名称/产品标识/描述
    FE->>M2: POST /api/products
    M2->>DB: 校验 productKey 唯一性
    alt productKey 重复
        M2-->>FE: 409 标识已存在
    else 通过
        M2->>DB: 插入 products(含 thing_model JSON 初值)
        DB-->>M2: productId
        M2-->>FE: 产品详情
    end

    A->>FE: 为产品添加 属性/服务/事件
    FE->>M3: POST /api/products/{id}/properties|services|events
    M3->>DB: 写入 product_properties/services/events(关系表)
    M3->>DB: 回读并重组 thing_model JSON
    M3->>DB: 更新 products.thing_model(双写一致)
    M3-->>FE: 保存成功
    FE->>FE: 调用 GET /api/products/{id}/thing-model 一次加载
```

**要点**
- 物模型聚合接口 `GET /api/products/{id}/thing-model` 直接返回 `thing_model` JSON，前端**一次加载**完整模型（满足 F3 设计目标）。
- 双写一致性风险：若关系表与 JSON 更新不一致，前端展示与运维查询会出现分歧。建议 v2.0 风险项"6. 物模型双写一致性"在详细设计中封装为统一服务层。

## 4. 设备接入与属性上报流程（IF-03）

设备侧经 MQTT 与平台交互。区分两类交互：**平台感知的上/下线事件**与**设备主动上报的属性**。

```mermaid
sequenceDiagram
    participant D as 设备 env_ctrl
    participant EMQX as EMQX(M0)
    participant M0 as M0 接入
    participant M4 as M4 设备管理
    participant M5 as M5 时序数据
    participant DB as MySQL(devices)
    participant TS as InfluxDB

    D->>EMQX: MQTT 连接(ProductKey+DeviceSecret)
    EMQX->>M0: 连接事件
    M0->>M4: 校验设备是否存在且启用
    M4->>DB: 查询 devices.status
    alt 设备不存在/已停用
        M4-->>EMQX: 拒绝连接
    else 启用
        M4->>DB: 写入 device_events(online 事件)
        EMQX-->>D: 连接成功
    end

    loop 周期上报
        D->>EMQX: publish 属性(air_temperature 等)
        EMQX->>M0: 桥接转发
        M0->>M5: 投递遥测消息
        M5->>M4: 校验设备启用 + 物模型字段
        M5->>TS: 写入 measurement=env_ctrl, tag=deviceName
        M5-->>EMQX: 确认
    end
```

**要点**
- 设备身份由 `ProductKey + DeviceName` 唯一标识，连接时校验 `DeviceSecret`（仅注册时明文一次，见 UC-G9）。
- 只读属性（air_temperature 等）走此上报路径；读写型阈值（temp_threshold 等）不在上报流，而由 IF-05 下发（设备本地存储）。
- 当前 F4/F5 接口未实现，表中 `devices`/`device_events` 已建，历史曲线查询依赖 InfluxDB 落地后才可用（v2.0 状态：F5 ⬜）。

## 5. 设备控制闭环流程（IF-04）

平台→设备的"服务"调用，需**下发与回执闭环**，关键在 `messageId` 关联与超时处理（对应 UC-G5）。

```mermaid
sequenceDiagram
    participant U as 种植户
    participant FE as 前端
    participant M6 as M6 设备控制
    participant M3 as M3 物模型
    participant M0 as M0 接入
    participant EMQX as EMQX
    participant D as 设备 env_ctrl
    participant DB as MySQL(device_commands)

    U->>FE: 点击 开/关风机
    FE->>M6: POST /api/devices/{id}/commands {service:set_fan, fan_state}
    M6->>M3: 校验 set_fan 输入参数结构
    M6->>DB: 插入 device_commands(messageId, status=已下发)
    M6->>EMQX: 下发 set_fan(fan_state, messageId)
    EMQX->>D: 下行指令
    D->>D: 执行 开/关风机
    D->>EMQX: 上行回执(messageId, result)
    EMQX->>M0: 回执转发
    M0->>M6: 回调 messageId 回执
    M6->>DB: 更新 status=成功
    M6-->>FE: 控制结果
    FE->>FE: 刷新 fan_status
```

异常分支（回执超时/设备离线）：

```mermaid
sequenceDiagram
    participant M6 as M6 设备控制
    participant EMQX as EMQX
    participant D as 设备 env_ctrl
    participant DB as MySQL(device_commands)

    M6->>EMQX: 下发 set_fan(messageId)
    alt 设备离线
        EMQX-->>M6: 无法投递
        M6->>DB: status=失败(离线)
        M6-->>FE: 提示设备离线, 可稍后重试
    else 在线但 10s 无回执
        M6->>M6: 启动超时计时(10s)
        M6->>DB: status=失败(超时)
        M6->>M6: 限次重试(默认 1 次)
    end
```

**要点**
- `messageId` 全局唯一，贯穿"下发→回执"，是控制闭环的关联键（F6 业务规则）。
- 仅**启用**设备可接收指令（M4 状态校验）。
- 设备端 `fan_status` 属只读属性，执行后会在下一次属性上报（IF-03）中回传，前端据此刷新开关状态。

## 6. 告警阈值配置与下发流程（IF-05）

种植户设定温/湿度告警阈值：既持久化到平台，又下发设备**本地存储**（满足 P-04"断网也能本地判断"）。

```mermaid
sequenceDiagram
    participant U as 种植户
    participant FE as 前端
    participant M3 as M3 物模型
    participant M8 as M8 告警
    participant M0 as M0 接入
    participant D as 设备 env_ctrl
    participant DB as MySQL(device_property_values)

    U->>FE: 填写 温度阈值 / 湿度阈值
    FE->>M3: PUT 属性 temp_threshold / humid_threshold(读写型)
    M3->>DB: 持久化 device_property_values
    FE->>M8: 调用 set_threshold(temp_max, humid_min)
    M8->>M0: 下发服务 set_threshold
    M0->>D: MQTT 下行(设备本地存储)
    D->>D: 更新本地阈值并用于本地判断
    D-->>M0: 回执 result
    M0-->>FE: 配置成功
```

**要点**
- 阈值有两条去向：① 平台 `device_property_values`（可被 `alarm_rules` 规则引用，IF-07 平台侧评估）；② 设备本地存储（断网时由设备端 `temp_alarm`/`dry_alarm` 事件直接判断，IF-07 设备侧触发）。
- 若设备离线，下发可标记为"待同步"，设备上线（IF-03 online）后补发。

## 7. 时序数据存储与查询流程（IF-06）

分三路：实时上报入库（接 IF-03）、历史查询、实时推送（WebSocket）。

```mermaid
sequenceDiagram
    participant FE as 前端
    participant M7 as M7 可视化
    participant M5 as M5 时序数据
    participant M0 as M0 接入
    participant TS as InfluxDB
    participant D as 设备 env_ctrl

    Note over D,TS: 实时入库(详见 IF-03)
    D->>M0: 属性上报
    M0->>M5: 投递遥测
    M5->>TS: 写入时序点

    FE->>M7: 选择设备 + 时间范围
    M7->>M5: GET /api/telemetry?deviceId&from&to
    M5->>TS: 查询 range
    TS-->>M5: 时序点数组
    M5-->>M7: 数据
    M7-->>FE: ECharts 渲染曲线

    Note over FE,M7: 实时刷新(WebSocket)
    M5->>M0: 新数据点事件
    M0->>M7: SocketIO 推送最新值
    M7-->>FE: 看板数字/仪表盘刷新
```

**要点**
- 实时数据优先走 WebSocket（SocketIO），降低轮询压力；历史走 REST 查询 InfluxDB。
- 查询性能目标：近 24h 查询 < 1s（非功能性需求 11）。

## 8. 告警触发与记录流程（IF-07）

告警存在**两类触发源**，均落 `device_events`：

1. **设备端触发**：设备按本地阈值判断后上报 `temp_alarm` / `dry_alarm`（断网也能触发，声光报警）。
2. **平台端触发**：平台依据 `alarm_rules` 规则引擎评估实时/入库数据，越限时生成告警。

```mermaid
sequenceDiagram
    participant D as 设备 env_ctrl
    participant M0 as M0 接入
    participant M8 as M8 告警
    participant M5 as M5 时序数据
    participant M3 as M3 物模型
    participant DB as MySQL(alarm_rules/device_events)
    participant FE as 前端

    Note over D,DB: 设备端触发
    D->>M0: 上报事件 temp_alarm(temperature,threshold)
    M0->>M8: 事件转发
    M8->>DB: 写入 device_events(level, status=未处理)

    Note over M5,DB: 平台端触发
    M5->>M8: 新数据点(air_temperature)
    M8->>DB: 读取 alarm_rules(启用)
    M8->>M3: 取指标定义
    M8->>M8: 评估 operator/threshold
    alt 越限
        M8->>DB: 写入 device_events(规则触发)
    end

    FE->>M8: GET /api/alerts?deviceId
    M8-->>FE: 告警流水(UC-G7)
    FE-->>FE: 界面提示 + 历史查看
```

**要点**
- 规则表 `alarm_rules` 与触发流水 `device_events` 解耦（数据模型决策 10.2）：规则是"配置"，流水是"发生过的事件"。
- 当前状态：F8 规则表与示例已建（air_temperature>35、soil_humidity<20），**触发引擎未实现**（v2.0 状态：F8 🟡）。
- 告警动作初版为"记录+界面提示"，短信/邮件/微信待确认（风险项 5）。

## 9. 权限拦截与行级隔离流程（IF-08）

观察员登录后只能看被授权数据、无任何控制入口（满足 O-02）。本流程体现 M9 横切复用。

```mermaid
sequenceDiagram
    participant O as 观察员
    participant FE as 前端
    participant M1 as M1 用户与鉴权
    participant M9 as M9 权限
    participant API as 业务模块(M4/M5/M7)

    O->>FE: 登录(角色=观察员)
    FE->>M1: POST /api/auth/login
    M1-->>FE: token(role=observer)
    O->>FE: 查看授权设备数据
    FE->>API: 请求带 token
    API->>M9: 校验 role + 数据归属
    alt 无 device:control 权限
        M9-->>FE: 403 禁止控制(无控制入口)
    else 仅查看授权设备
        M9-->>API: 放行(限定 deviceId 范围)
        API-->>FE: 仅授权设备数据
    end
```

**要点**
- JWT 携带 `userId` 与 `roles`，M9 中间件按"角色 + 行级归属"过滤：种植户只看自己名下设备，观察员只看被授权设备。
- 授权关系（种植户→观察员）对应 UC-G8，需新增**授权关系表**（v2.0 风险项 7），当前未细化。
- 当前 F9 仅 JWT、无角色拦截（v2.0 状态：F9 ⬜），本流程为待实现目标态。

## 10. 异常与边界交互（IF-09）

汇总跨流程的异常与补偿机制，避免在主流程图中过度展开。

| 异常场景 | 触发条件 | 处理策略 | 涉及模块 |
| --- | --- | --- | --- |
| 设备离线指令 | 下发时设备未连接 | 标记失败(离线)，界面提示，可手动重试；上线后补发 | M6、M0 |
| 回执超时 | 在线但 10s 无回执 | 标记失败(超时)，限次重试(默认 1 次) | M6 |
| 断网数据补报 | 设备网络中断 | 设备本地缓存遥测，联网后批量补报（断网声光报警仍本地触发） | 设备、M5 |
| 阈值下发离线 | 配置时设备离线 | 标记待同步，online 事件后补发 set_threshold | M3、M8、M0 |
| 重复标识 | productKey / identifier / deviceName 重复 | 返回 409，拒绝写入 | M2、M3、M4 |
| 凭据错误/冻结 | 登录校验失败 | 401 / 403，提示明确原因 | M1 |
| 未认证/越权 | 缺 token 或角色不符 | 401 / 403，中间件统一拦截 | M9 |

```mermaid
sequenceDiagram
    participant D as 设备 env_ctrl
    participant M0 as M0 接入
    participant M4 as M4 设备管理
    participant M6 as M6 设备控制
    participant DB as MySQL

    D->>M0: 离线期间缓存遥测
    D->>M0: 网络恢复, 批量补报
    M0->>M4: online 事件(网络恢复)
    M4->>DB: 更新 devices.status=启用
    M6->>DB: 扫描 待同步指令/待下发阈值
    M6->>M0: 补发 set_fan / set_threshold
    M0->>D: 下行补发
```

## 11. 跨模块交互总览（消息主干）

下图汇总"一次典型业务"在模块间的纵向调用主干，与 v2.0 第 6.4 节模块依赖图互为补充（该图看静态依赖，本图看动态调用顺序）。

    participant M2 as M2 产品
    participant M3 as M3 物模型
    participant M4 as M4 设备
    participant M5 as M5 时序
    participant M6 as M6 控制
    participant M8 as M8 告警
    participant M0 as M0 基础设施

    U->>M2: 建产品(IF-02)
    M2->>M3: 定义物模型
